# ДЗ.1: независимая проверка MILEAGE

Дата: 15 октября 2026 года. Проверенное исходное состояние: `b20a33d`, ветка
`hw1/dz1-AnnaSoboleva`. Статический аудит выполнен отдельным агентом на модели
`gpt-6-astra`; результаты запусков ниже добавлены основным агентом отдельно.

## Вердикт

Все семь REQ имеют проверки на уровне домена, сервиса или валидатора.
Дополнительных бизнес-требований сверх `docs/intent/intent_MILEAGE.md` в
спецификации не обнаружено. Реализация соответствует intent: правило понижает
только `approve` до `review`, не изменяет валидационный лимит и возвращает
нулевой лимит при понижении.

Полное выполнение учебного процесса пока не подтверждено: Git-история не
показывает отдельный красный тест до реализации; запуск Docker/MySQL и ручная
проверка в браузере не выполнены. Это ограничения результата, а не успешные
проверки.

null закрепляют сохранённый лимит и обязательность поля. Новых LTV-правил,
изменений frontend, схемы БД или задачи LOAN-12 реализация не добавляет.

Единственный Open question intent — имя поля и код причины — явно перенесён
в spec и закрыт первой версией плана: `review_reason` /
`mileage_over_threshold`.

## Где агент срезал угол

Агент приравнял проверки домена и сервиса к полному покрытию API-критериев и
использовал константу реализации вместо независимого ожидания точной строки
публичного кода причины. В исходном плане остались две противоречащие версии:
первая описывает отдельный `MileageRule`, вторая — изменение `DecisionEngine`.
Код соответствует первой версии. Новые тесты не содержат обязательных
комментариев `// Arrange`, `// Act`, `// Assert`. В коммите `589fb45` сохранены
одновременно spec, план, тесты и production-код: последовательность «красный
тест → зелёный код» по этим коммитам не доказана. Задним числом выдавать такую
историю за TDD нельзя.

Вспомогательные `.kilo/plans/` и изменение `docs/setup/agents.md` также
выходят за закрытый перечень файлов исходной первой версии плана. Это
расхождение процесса, а не новое бизнес-требование.

## Фактическая проверка основным агентом

В системе не найдены PHP, Composer, make и Docker в PATH. В игнорируемую
`tmp/dz1-tools/` загружен официальный PHP 8.3.35 для Windows; SHA-256 архива
проверен по метаданным windows.php.net. Зависимости vendor уже присутствовали.

Выполнена команда, соответствующая PHPUnit-части `make test`:

```powershell
./tmp/dz1-tools/php83/php.exe -d extension_dir=tmp/dz1-tools/php83/ext -d extension=mbstring vendor/bin/phpunit --colors=never
```

Результат: **43 теста, 69 проверок, успешно**. Синтаксис всех 22 PHP-файлов из
backend и tests проверен через `php -l`, ошибок нет. Буквально `make test` и
`make lint` не запускались: выполнялись их PHP-проверки напрямую.

Временный smoke-скрипт вызвал реальный HTTP-слой Slim через
`AppFactory::create(new PDO('sqlite::memory:'), $rules)` и `App::handle`.
Проверены маршрутизация, контроллер и JSON для POST `/api/ltv`; сохранение в
БД этот маршрут не выполняет. Контроллеру передавался уже разобранный body,
поэтому разбор сырого JSON по сети этим запуском не проверен.

## Исправления после аудита и выбор модели

Основной агент удалил из плана дублирующую устаревшую версию, сохранил
актуальную реализацию через MileageRule, явно описал порядок красного и
зелёного этапов и отделил соответствие AC от доказательства запуска.
Production-код и существующие тестовые проверки при этом не изменялись.

Были запущены Kilo CLI 7.8.8 с учебными GLM 5.3 и MiniMax M3, однако ответы
от учебного провайдера не получены; эти процессы остановлены. Проверочный
запрос GLM 5.3 через Kilo Gateway вернул `Add credits to continue`.
15 октября пользователь разрешил завершить работу доступной моделью с
честной пометкой. Исправление плана и оформление результата выполнены
основным агентом Codex; успешную работу GLM/MiniMax этот отчёт не заявляет.

## Ограничения сдачи

- Закрепить API-контракт постоянными тестами, включая буквальный код причины
  и наличие поля при null, если требуется полное автоматическое покрытие AC.
- Привести новые тесты к AAA, не ослабляя проверок.
- Запустить `make up` на машине с Docker и вручную проверить заявку 400001 в
  браузере; сохранить реальный результат.
- Зафиксировать, что исходный TDD-порядок коммитов не подтверждён.
- По последующей прямой просьбе пользователя результат передаётся одним PR;
  перечисленные ограничения не выдаются за выполненные проверки. Сам отчёт
  не подтверждает прохождение CI.
